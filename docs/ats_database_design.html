ATS media house: Database Design

Booking & Airtel Money payment system · Conceptual → Logical → Physical · CRUD · ACID

1. Conceptual design (Chen ER diagram)

The conceptual model describes the business and ignores the DBMS. There are four entity types: Customer, Service (photography package), Booking and Payment.

Notation (Chen): rectangle = entity · diamond = relationship · ellipse = attribute · underlined = key attribute · double line = total participation · 1/N = cardinality. Technical logging attributes (airtel_response, error) are left out of the diagram and appear in the physical design.

Relationships and business rules

RelationshipEntitiesCardinalityParticipation / rule
MakesCustomer – Booking1 : NEvery booking belongs to exactly one customer (total). A customer is identified by phone number.
Is_forService – Booking1 : NEvery booking is for exactly one package (total). A package may have no bookings yet.
Settled_byBooking – Payment1 : NA payment belongs to exactly one booking (total). A booking can have several attempts (failed, then successful).

State rules: booking pending_payment → paid | cancelled; payment PENDING → SUCCESS | FAILED. Final states never change. Customer–Booking, Service–Booking and Booking–Payment are all 1:N, so no M:N relationship needs a junction table.

2. Logical design (relational model)

Mapping rules: each entity becomes a relation, each 1:N relationship becomes a foreign key on the N side, and key attributes become primary keys. Underlined = PK, italic = FK.

CUSTOMER ( customer_id, full_name, phone [UNIQUE], email, created_at, updated_at )
SERVICE  ( service_id, code [UNIQUE], label, price, is_active )
BOOKING  ( booking_id, customer_id → CUSTOMER, service_id → SERVICE, amount_due,
           event_date, notes, status, created_at, updated_at )
PAYMENT  ( transaction_id, booking_id → BOOKING, msisdn, amount, status,
           airtel_response, error, created_at, last_checked )

Normalisation

FormHow it is met
1NFAll attributes are atomic. No repeating groups. Every table has a primary key.
2NFAll primary keys are single columns, so no partial dependencies exist.
3NFThe old flat bookings table repeated full_name, email (determined by phone) and service_label, price (determined by service). These moved into CUSTOMER and SERVICE, which removes the transitive dependencies.
Deliberate exceptionamount_due and payments.amount copy the price at the time. If the package price changes later, old bookings and receipts must keep the price actually charged. This is a controlled snapshot, not an anomaly.

3. Physical design (MySQL / MariaDB on XAMPP)

The full DDL is in schema.sql. Every table uses the InnoDB engine, which supplies transactions, row-level locks, foreign keys and crash recovery.

TableColumns and typesKeys, indexes, constraints
customerscustomer_id INT UNSIGNED AI · full_name VARCHAR(120) · phone CHAR(9) · email VARCHAR(160) NULL · created_at/updated_at TIMESTAMPPK(customer_id) · UNIQUE(phone) · CHECK phone is 9 digits
servicesservice_id TINYINT UNSIGNED AI · code VARCHAR(20) · label VARCHAR(60) · price DECIMAL(10,2) · is_active TINYINT(1)PK · UNIQUE(code) · CHECK price > 0
bookingsbooking_id VARCHAR(32) · customer_id · service_id · amount_due DECIMAL(10,2) · event_date DATE · notes TEXT · status ENUM('pending_payment','paid','cancelled') · timestampsPK · FK→customers, FK→services (ON DELETE RESTRICT) · INDEX(customer_id), INDEX(service_id,event_date), INDEX(status) · CHECK amount_due > 0
paymentstransaction_id VARCHAR(32) · booking_id · msisdn CHAR(9) · amount DECIMAL(10,2) · status ENUM('PENDING','SUCCESS','FAILED') · airtel_response TEXT · error TEXT · created_at · last_checkedPK · FK→bookings (RESTRICT) · INDEX(booking_id,status) · CHECK amount > 0

Design choices: money uses DECIMAL (never FLOAT). Phones are stored as a normalised 9-digit MSISDN, so 0972971151 and +260972971151 match the same customer. RESTRICT prevents deleting a record that financial history depends on.

5. ACID properties

PropertyWhere and how it is implemented
AAtomicitywith_tx() in helpers.php wraps each multi-step change in BEGIN / COMMIT, with ROLLBACK on any exception. Examples: customer upsert + booking insert; payment status + booking status → paid in one unit, so a payment can never be SUCCESS while its booking stays unpaid.
CConsistencyPK, UNIQUE, FK, CHECK and ENUM constraints, plus strict SQL mode (no silent truncation). The price always comes from the database, never from the browser. State rules are enforced in code (paid bookings cannot be edited or deleted; final payment states are immutable).
IIsolationInnoDB default REPEATABLE READ plus explicit SELECT … FOR UPDATE row locks on the booking or payment being changed. This stops double payment prompts, double settlement and edits during payment. The Airtel HTTP call runs outside the transaction, so locks are never held during network waits.
DDurabilityInnoDB redo log with innodb_flush_log_at_trx_commit=1 (keep this value). The PENDING payment row is committed before Airtel is called, so even if PHP crashes after the prompt is sent, the transaction is on disk and can be settled later.

To verify, run health.php. It reports an error if any table is not InnoDB.
